# Февральский rolling backtest (2026)

Это историческая **симуляция выпуска прогнозов**, а не расчёт точности на
февральских фактических значениях. Фактическая мощность февраля не предоставлена;
при прогоне не читаются ни февральский SCADA target, ни измеренная будущая погода.

## Политика времени выпуска

Календарь станции — `Asia/Almaty`; все метки в CSV и JSON записаны в UTC.
Один выпуск в 00:00 местного времени каждого дня **с 31 января по 28 февраля
включительно** (29 выпусков). Первый `issue_time` — `2026-01-30T19:00:00Z`,
последний — `2026-02-27T19:00:00Z`. Каждый выпуск содержит ровно 48 будущих
почасовых точек для каждой из двух турбин. Поэтому полный журнал включает
также часы вне февраля: они остаются частью исходных выпусков, но не оценки.

Для первого выпуска модель должна быть уже выбрана к 31 января 00:00 местного
времени. Обучение архивной погодной модели использует только декабрьские и более
ранние target-значения; выбор между ExtraTrees и HistGradientBoosting использует
только январские почасовые target-значения, закончившиеся **не позже** этого
момента. На практике это 1–30 января (1440 строк на турбину с двумя lead-группами).
Целевые значения 31 января остаются только в отчётных январских метриках и не
могут изменить модель первого выпуска. Предполагается доступность SCADA-среднего
сразу после окончания часа; фактическая задержка доставки не задана.

## Источник и безопасный погодный выпуск

Используется Open-Meteo **Single Runs** для `ecmwf_ifs`: отдельный исторический
модельный запуск с явно указанным `weather_run_time`, а не наблюдение, reanalysis
или последующий actual. Выбирается самый свежий 00/06/12/18 UTC run, для которого
`weather_run_time + 6 часов <= issue_time`; если он недоступен, допускается
ровно один более старый шестичасовой run. При отсутствии обоих выпуск явно
помечается `FAILED`, без подмены погоды. Шесть часов — консервативная задержка
публикации, а не подтверждённый фактический timestamp публикации каждого run.

Для каждой точки проверяется `weather_run_time + 6h <= issue_time < valid_time`.
Также проверяются источник, SHA-256 запроса и ответа погоды, время доступности
выбранной модели, равномерные целые lead-часы, полнота обеих турбин и диапазон
мощности `[0, 1]`. Сохранённый JSON сравнивается с результатом агента. Ранее
сохранённый JSON не перезаписывается при конфликтующем содержимом.

## Горизонт и перекрывающиеся прогнозы

`lead_hour = (valid_time - issue_time)` в целых часах. Полный журнал каждого
выпуска сохраняет lead 1–48; **в февральскую оценочную таблицу допускаются
только lead 24–48**. Для пары `(turbine_id, valid_time)` выбирается строка с
максимальным `issue_time` среди допустимых. Точный дубликат
`issue_time/turbine_id/valid_time` считается ошибкой. При ежедневном выпуске
выбранные февральские lead фактически равны 24–47: lead 48 перекрывается более
свежим выпуском с lead 24. Например, на 00:00 местного 2 февраля выбирается
выпуск 1 февраля 00:00 (lead 24), а не 31 января (lead 48).

## Файлы и воспроизведение

- `data/forecasts/rolling/forecast_*.json` — все 29 исходных выпусков с
  `issue_time`, погодным run, моделью и provenance; новые входы получают новую
  версию, старые выпуски не удаляются.
- `data/forecasts/rolling_forecasts.csv` — все 2784 прогноза
  (`29 × 48 × 2`), включая перекрытия и часы вне февраля.
- `data/forecasts/february_evaluation.csv` — ровно 1344 строки, одна на каждый
  из 672 местных февральских часов и каждую турбину. Это **prediction-only**
  таблица, без фактических значений мощности.
- `data/forecasts/rolling_report.json` — статусы всех выпусков, счётчики,
  проверенные границы, правило отбора и явная отметка `COMPLETE/INCOMPLETE`.

Поля каждой CSV-строки: `issue_time`, `weather_run_time`, `valid_time`,
`turbine_id`, `lead_hour`, `predicted_normalized_power`, `model_version`,
`weather_input_hash` (SHA-256 параметров погодного запроса),
`weather_response_sha256` (SHA-256 исходного ответа), `forecast_input_hash`
(SHA-256 полного входа агента) и `model_available_at`. Все временные поля
содержат UTC-суффикс `Z`. Погодный cache не хранится в Git.

```powershell
# После подготовки processed SCADA, baseline-артефактов и архива обучения:
python -m ai.models.train --scada-timezone Asia/Almaty
python -m ai.services.archive_download --start 2026-01-30T19:00:00Z --end 2026-02-27T19:00:00Z --step-hours 24 --workers 1
python -m ai.services.rolling_backtest --cache-only
python -m unittest discover -s tests -v
```

Первый download требует доступа к Open-Meteo; повторяйте ту же команду после
HTTP 429 — успешные запросы уже закешированы. `--cache-only` предотвращает
неожиданную подмену данных или тихую сетевую загрузку при повторной проверке.
При недоступности архива симуляция остаётся `INCOMPLETE` и завершается с кодом 1.

## Валидация и ограничения

Обучение: фактически 30 ноября 2025 20:00 — 31 декабря 2025 23:00 местного
времени; январь 2026 — хронологическая validation. Выбор production-модели
основан только на доступной к первому issue части января; полный январь
используется для отчётных MAE/RMSE/R². Для обеих турбин выбран архивно-погодный
HistGradientBoosting. Точные строки, признаки, версии и метрики находятся в
`ai/models/artifacts/metrics.json` и `*_archived_training_rows.csv`.

**Февральских MAE/RMSE/R² нет:** февральский target отсутствует. Модель
обучалась преимущественно около lead 24 и 48 часов (±3 часа); качество lead
28–44 отдельно не подтверждено. Архив Open-Meteo и правило шестичасовой
задержки позволяют воспроизвести консервативный replay, но не доказывают
фактическое время публикации каждого исторического выпуска. Старый
`ai.services.replay` с выпусками в 23:00 остаётся дополнительным техническим
прогоном; официальная оценочная таблица строится только этим модулем.
